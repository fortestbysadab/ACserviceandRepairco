# Sheetal platform — app + API (Phase 1 scaffold)

Next.js App Router service that will host the **customer portal**, the **expert portal**
and the **WhatsApp webhook** for the Kolkata / Howrah pilot. The public marketing page
stays on the static Render site — this service never serves it.

Phase 1 scope is deliberately infrastructure-only: it boots, connects, migrates, reports
health and exposes the queue-drain endpoint the outbox will use.

---

## What's here

```
platform/
├── src/app/page.tsx                  status page (replaced by /login in Phase 2)
├── src/app/api/health/route.ts       liveness + database round-trip  (Render health check)

├── src/lib/db/index.ts               pg pool + Drizzle client + pingDb() + withTransaction()
├── src/db/schema.ts                  Phase 1 tables (identity, membership, session, queue)
├── src/db/migrations/0001_init.sql   the SQL that actually runs
├── scripts/migrate.mjs               transaction + advisory-lock migration runner
└── drizzle.config.ts                 `npm run db:generate` for schema diffs
```

Tables created in Phase 1: `identity`, `membership`, `session`, `inbound_event`,
`outbox`, `delivery_event`. Domain tables (`customer`, `technician`, `zone`, `asset`,
`job`, `quote_version`, `resource_block`, `payment`, `warranty_claim`, `consent`,
`reminder`) come in Phase 2, because their constraints encode business rules that deserve
a review pass first.

## Deploy on Render (free tier)

### 1. Create the database — Neon, region Singapore
1. neon.tech → **New Project** → region **AWS ap-southeast-1 (Singapore)**.
2. Copy **two** connection strings from the dashboard:
   - **Pooled** (host contains `-pooler`) → `DATABASE_URL`
   - **Direct** (no `-pooler`) → `DIRECT_DATABASE_URL`
3. Append `?sslmode=require` if Neon didn't.

Why not Render Postgres? Its free instance is **deleted 30 days after creation** — not
acceptable for receipts and warranties. Neon free has no expiry and resumes in ms.

### 2. Create the app service
Dashboard → **New + → Web Service** → pick this repo, then:

| Field | Value |
|---|---|
| Name | `sheetal-app` |
| Language / Runtime | Node |
| **Root Directory** | `platform` |
| Region | Singapore |
| Instance Type | Free |
| Build Command | `npm ci && npm run build` |
| Start Command | `npm run db:migrate && npm start` |
| Health Check Path | `/api/health` |

> If you prefer the Blueprint route, `../render.yaml` defines this service — but **delete
> the `sheetal-site` block first** if you already created the static site by hand,
> otherwise you'll get a duplicate.

### 3. Environment variables
`SESSION_SECRET` and `CRON_SECRET` are auto-generated by the blueprint. Set the rest:

| Key | Value |
|---|---|
| `DATABASE_URL` | Neon **pooled** string |
| `DIRECT_DATABASE_URL` | Neon **direct** string |
| `APP_ORIGIN` | `https://www.yourdomain.in` |
| `COOKIE_DOMAIN` | `.yourdomain.in` |
| `GEMINI_API_KEY`, `R2_*`, `META_*` | leave empty for now — optional at boot |

### 4. Verify
```bash
curl -s https://app.yourdomain.in/api/health | jq
# { "status": "ok", "checks": { "database": { "ok": true, "latencyMs": 62 } }, ... }
```

### 5. Turn on the sweep
The workflow ships as `ops/github/dispatch-sweep.yml` (GitHub only accepts files under
`.github/workflows/` from a token with the **`workflow`** scope). Enable it either way:

```bash
git mv ops/github/dispatch-sweep.yml .github/workflows/dispatch-sweep.yml
git commit -m "chore: enable dispatch sweep" && git push
```
or paste the file in the GitHub web UI: **Actions → New workflow**.

Then GitHub → repo **Settings → Secrets and variables → Actions**:
- Secret `CRON_SECRET` — same value as the Render env var
- Variable `APP_BASE_URL` — `https://app.yourdomain.in`

It runs every 5 minutes. Phase 1 has nothing in the outbox, so this is optional until the
WhatsApp work lands. When the app moves to a paid instance type, enable the
`sheetal-dispatch` cron block in `render.yaml` and delete the workflow.

## Custom domain (do this before launch)

Cookies must be **same-site**. Use one registrable domain for both services:

| Host | Service | Render setting |
|---|---|---|
| `www.yourdomain.in` | static site | Custom Domain |
| `app.yourdomain.in` | this service | Custom Domain |

Then `COOKIE_DOMAIN=.yourdomain.in` lets the session cookie flow between them without
`SameSite=None` — which Safari and Chrome increasingly block. Never mix
`*.vercel.app` with `*.onrender.com`.

## Free-tier constraints this design works around

| Constraint | How the scaffold handles it |
|---|---|
| Free web services sleep after ~15 min idle | Interactive work runs **inline** in the request; the queue only carries side effects. First hit after sleep is slow — expected during the pilot. |
| ~750 instance-hours / month, i.e. one always-on service | Exactly one app service. No separate staging service — use a Neon branch for preview data instead. |
| Render cron jobs need a paid instance type | `/api/cron/dispatch` is called by GitHub Actions every 5 min; swap to the real cron later with no code change. |
| No object storage | Cloudflare R2 (10 GB free, zero egress) with presigned URLs — added in Phase 2 for evidence photos. |
| 0.1 CPU / 512 MB | Bounded batches (`BATCH = 25`), `maxDuration = 60`, pool `max = 5`. |
